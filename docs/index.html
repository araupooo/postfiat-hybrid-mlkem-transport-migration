Hybrid ML-KEM Transport Migration Assessment

Assessment of migrating the PFTL peer-to-peer overlay transport to hybrid classical-plus-ML-KEM key exchange, for the pinned postfiatd tree 0085a1ff885d6a446369cf73a4430f75af22be55: a gap analysis of what the tree actually contains on the transport key-exchange path, reproducible local-fixture handshake benchmarks (hybrid X25519+ML-KEM-512/768/1024 against the classical X25519 baseline), a negotiation and downgrade analysis, and a key-compromise response and rollback plan. Local fixtures only; no live-network testing, no mutation of the pinned tree.

Headline finding. The pinned tree has no key-exchange primitive at all on the transport path (F-01): peer TLS uses an anonymous context with an ephemeral self-signed RSA certificate and verify_none, authentication happens at the application layer via a secp256k1 session signature bound to the TLS Finished messages, and there is no TLS group/curve configuration anywhere — so there is no hook point where a hybrid group could be selected today. A migration must add the KEM, the negotiation, and the key storage; it cannot reuse the node identity (always secp256k1) as a KEM key. The measured cost is small: the hybrid handshake was roughly 1.2-1.7x the classical one across repeated runs on the build machine (exact figures for this run: results/timing_measurements.txt). No Critical or High finding.

  hypothesis: One hundred hybrid handshakes generate one hundred distinct encapsulation keys and one hundred distinct shared secrets: a compromised session key exposes only that session.
  result: PASS
  ML-KEM-512: 100 handshakes -> 100 distinct encapsulation keys, 100 distinct shared secrets OK

  ML-KEM-1024: 100 handshakes -> 100 distinct encapsulation keys, 100 distinct shared secrets OK
  forward secrecy (model): keys are ephemeral per handshake, so compromise of one session key does not retroactively expose past sessions OK

[CHECK K32] Key-compromise rotation maps to config-only steps (TESTED)
  hypothesis: Every rotation step for a compromised KEM key maps to a config change, an operator action, or a restart — no step requires a code change — because keys are loaded once at startup from configuration, exactly like the existing validator keys.
  result: PASS
  1. Revoke the compromised KEM key in the operator's key inventory (the key itself is never stored in the tree).
    mechanism: operator action; anchor: no KEM key material exists in the tree (gap analysis K02/K13)
  2. Generate a fresh ML-KEM keypair for the affected parameter set.
    mechanism: operator action (offline); anchor: ML-KEM key generation is a library operation; no tree code involved
  3. Publish the new encapsulation key in the operator's peer configuration (the new [kem] config section the migration adds).
    mechanism: config change; anchor: config sections are declared in src/xrpld/core/ConfigSections.h; validator keys already follow this pattern via [validator_token] (ConfigSections.h:96)
  4. Restart the node so the new key is loaded at startup.
    mechanism: restart; anchor: node identity and keys are loaded once at startup: src/xrpld/app/main/Application.cpp:1378 (nodeIdentity_ = getNodeIdentity(...))
  5. Old sessions are unaffected: each handshake used fresh ephemeral keys, so a compromised long-term KEM key does not retroactively expose past sessions.
    mechanism: forward secrecy (ephemeral keys); anchor: harness check K31: every handshake iteration generates fresh ephemeral keys and distinct shared secrets
  rotation is config + restart: the new key is published in configuration and loaded at startup (Application.cpp:1378) OK
  the tree's existing pattern is [validator_token] (ConfigSections.h:96); the migration adds an analogous KEM key section OK

[CHECK K33] Rollback to classical-only is policy-only (TESTED)
  hypothesis: Every rollback step is a policy or config change: no tree code is removed or changed, because the tree contains no KEM code to remove (K02) and the hybrid path lives outside the pinned tree until a migration lands.
  result: PASS
  1. Change the local negotiation policy from require-hybrid (or prefer-hybrid) to allow-classical.
    mechanism: policy change; anchor: policy is a local operator setting, not tree code
  2. Peers that still offer hybrid algorithms keep negotiating hybrid; peers that do not fall back to classical X25519.
    mechanism: negotiation model; anchor: scripts/negotiation.py negotiate('allow-classical', ...)
  3. No tree code is removed or changed: the tree contains no KEM code to remove, and the hybrid code path lives outside the pinned tree until a migration lands.
    mechanism: no code change; anchor: gap analysis K02: 0 ML-KEM files in the pinned tree
  4. Re-enable hybrid later by reversing step 1; no key material is invalidated by the rollback.
    mechanism: policy change; anchor: negotiation model; no persistent KEM state in the tree
  model check: allow-classical accepts classical-only peers and still prefers hybrid when offered OK
  rollback is reversible: re-enabling hybrid is the reverse policy change; no key material is invalidated OK
